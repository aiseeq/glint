Контекст
- glint (github.com/aiseeq/glint) — универсальный статический анализатор Go/TypeScript.
- Авторитетный список правил и их категорий — `glint rules`; README вторичен, количество правил в тексте не фиксировать.
  Зачем: число и перечень правил в текстах не расходятся с кодом
- Потребители — закрытые проекты автора. Находки, которые у них даёт правка glint, чинят мастера этих проектов: в их код отсюда не ходить, задание им — тикетом (скилл `dev-process`, `masters.md`).
  Зачем: код проекта-потребителя не правится из сессии glint мимо его мастера
- Репозиторий публичный: чего в нём не должно быть — скилл `dev-process`, `git.md`, «Публичный репозиторий». Своё: репро реальной находки переписывать на синтетические имена (projectA/payprov-стиль), без функций и путей закрытого проекта; какую багу ловит правило, документирует его тест, а не сообщение коммита.
  Зачем: вместе с репро реальной находки в публичный репозиторий не попадают имена, функции и пути закрытого проекта
- Утечка в выпущенной истории: имена и данные закрытых проектов работодателя вычищаются переписыванием истории. Остальное — имена функций, личные репозитории автора — не утечка: историю ради этого не переписывать и не предлагать.
  Зачем: рабочие имена не остаются в выпущенной истории, а ради остального историю публичного репозитория не переписывают

Сборка и проверки
- Правка, меняющая охват правила (новое правило, снятое освобождение файла или пути, новое допущение), — до `graft install` `graft consumers` и разбор каждой новой находки: ложная — назад к TDD-репро, верная — агенту потребителя. Установка сразу роняет гейт каждого потребителя на новой находке. Правило с десятками ложных на живом проекте не ставить.
  Зачем: релиз glint не роняет гейты всех проектов ложными находками
- Потребители получают glint только через `graft install`: после изменения правил переустановить. В бинарь вшивается `graft version --describe` (теги `v*`, `version.mode: git-tag`), её печатает `glint --version`.
  Зачем: потребители не остаются на старой версии правил после правки
- Тег релиза ставит `graft install` на main (HEAD без тега); ручной `graft release` — только для `--minor`/`--major`.
  Зачем: тег релиза стоит на том, что прошло все проверки установки и ушло потребителям

Правила анализатора
- Новое правило и фикс начинаются с TDD-репро реальной находки: красный тест с синтетическим аналогом реального кода, затем правка правила. Ложное срабатывание чинить в правиле.
  Зачем: правило меняют по воспроизведённой находке, а ложное срабатывание чинят для всех потребителей, а не глушат в одном
- Path-sensitive правила писать на generic `patternkit.FlowWalker` (pkg/rules/patterns/internal/patternkit/flow_walker.go), а не на собственном обходе потока управления.
  Зачем: path-sensitive правила не расходятся в обходе потока управления и его ошибках
- Список путей в flow-правилах объединять только через `patternkit.JoinFlowPaths` (там же, flow_paths.go) с ключом пути: `append(left, right...)` даёт 2^N путей.
  Зачем: flow-правило не съедает память на больших функциях
- При `packages.Load(Tests:true)` пакет приходит вариантами (`P`, `P [P.test]`, `P.test`, `P_test [P.test]`) с разными `*types.Named`. Если сигнатура метода интерфейса упоминает именованный тип пакета, `types.Implements` между вариантами даёт false, и живой интерфейс выглядит мёртвым. Поэтому проверять каждый вариант, а реализации сводить по позиции объявления.
  Зачем: живой интерфейс не объявляется мёртвым из-за вариантов пакета при загрузке с тестами
- Выход майнинга истории потребителя (batch-*.tsv, *.jsonl, манифесты) сразу класть в `~/.local/share/glint-history/<проект>/`, не только в scratchpad.
  Зачем: выход майнинга не теряется вместе со scratchpad сессии: так уже было
