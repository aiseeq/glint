Контекст
- glint (github.com/aiseeq/glint) — универсальный статический анализатор Go/TypeScript.
- Правила разложены по 8 категориям (architecture, duplication, patterns, typesafety, security, deadcode, naming, documentation). Авторитетный список — `glint rules`; README вторичен, количество правил в тексте не фиксировать.
- Single-pass: файлы читаются и парсятся один раз, AST-кэш, параллельное выполнение. YAML-конфиг с наследованием и per-rule exceptions, autofix для части правил, вывод console/JSON/summary.
- РАЗРАБОТКА НА ПРИМЕРАХ РЕАЛЬНЫХ ПРОЕКТОВ: главные потребители — закрытые проекты автора; их локальные пути перечислены в untracked-файле `.glint-parity` (создать при отсутствии, в git не коммитить). Новые правила и фиксы — TDD-репро с реальных находок. Универсальные правила живут здесь; проектно-специфичные — в линтере соответствующего проекта, сюда их не добавлять.
- ПУБЛИЧНАЯ РЕПА — БЕЗ ВНУТРЕННИХ ИМЁН: в коде, тестах, комментариях и сообщениях коммитов запрещены имена закрытых проектов и работодателя, номера внутренних тикетов (SI-NNN и подобные), имена провайдеров/интеграций закрытых проектов, их внутренние функции и пути. Репро переписывать на синтетические имена (projectA/payprov-стиль); какую багу ловит правило, документирует его тест, а не коммит-сообщение. Перед push проверить diff и текст коммита на эти утечки.

Сборка и проверки
- `make build`; `make install` — установка в ~/bin. После изменения правил переустановить, иначе потребители не увидят новую версию.
- `make test | check` (fmt-check vet lint test test-race) | `self-check` (glint на самом себе).
- ПАРИТЕТ ПОСЛЕ ИЗМЕНЕНИЯ ПРАВИЛ: прогнать self-check и сверить количество находок на реальных проектах из `.glint-parity` до и после; изменение количества объяснить в резюме (в резюме и коммите проекты называть обезличенно).
- `make commit` запускает только `make smoke`. Полный `make check` и impact-проверки — по риску изменения и обязательно перед release, не перед каждым промежуточным коммитом.

Правила анализатора
- ЛОЖНЫЕ СРАБАТЫВАНИЯ ЧИНИТЬ В ПРАВИЛЕ: false positive → TDD-репро (красный тест с реальным кодом) → фикс правила. Suppress в целевом проекте — только для документированных легитимных случаев, не вместо фикса правила.
- Баг → сначала тест, воспроизводящий его (красный, с реальным кодом-репро из целевого проекта) → фикс → зелёный.
- У правил много общей инфраструктуры (core.LineSuppresses, реестр, AST-хелперы) — перед написанием кода искать существующее.
- Утверждения из README и комментариев (количество правил, поведение) не переносить без проверки: `glint rules`, запуск на тест-кейсе.

Коммиты
- `make commit MESSAGE="..."` — smoke + stage all + commit + push во все remotes; отдельный `git push` после него не запускать. Разрешён без запроса, так часто, как нужно; после задачи — коммит и push, при массовых правках — промежуточные.
- Без запроса разрешены: read-only команды, `git fetch`, `git switch <existing-branch>`, `git switch -c <branch> origin/main`, `git branch --set-upstream-to=...`, `git merge --ff-only`, `git pull --ff-only`.
- Требуют разрешения: `add`, raw `commit`, `reset`, `restore`, `checkout --`, `clean`, `stash`, `rebase`, `cherry-pick`, обычный merge, удаление веток, force-push, теги.
- Перед коммитом смотреть только на секреты и большие бинарники. MESSAGE — Conventional Commits.

Правила работы
- После ошибки — явный error (сигнатура с error) + лог. Фолбек к default/magic/0/""/nil запрещён, неоднозначный ввод — тоже ошибка; стратегию выбирает caller. Явный фолбек по дизайну разрешён и логируется.
- Одна логика на действие; найден второй участок с той же логикой — свести к единому источнику сразу.
- Причину чинить, а не обходить: падающие проверки (тесты, lint) чинить, а не отключать.
- Отладка: сначала evidence (реальный вывод glint на тест-кейсе, AST-дамп, логи), потом гипотеза, потом фикс.
- Перед фиксом или новой функциональностью — официальная документация (go/ast, go/types, tree-sitter) и WebSearch; готовое проверенное решение предпочтительнее самописного.
- Факты выяснять своими инструментами (grep, запуск glint на тест-кейсе, git log); спрашивать только о недоступном или о замысле.
- После правки: кто ещё вызывает? что при частичном сбое? какие defaults/конфиги влияют? Сомнение — явно в вывод.
- Пользователь сообщил о проблеме — искать, пока не найдена.
- Побочно замеченные проблемы называть в финале.
- Написал код или правило — сразу запустил тесты и self-check.
- Deprecated-алиасы не создавать. Legacy не расширять; рефакторинг legacy — отдельной задачей.
- Не запускать фоновую команду или суб-агента, если после запуска остаётся только ждать: делать inline, распараллеливать или активно мониторить.
